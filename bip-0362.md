## Abstract

This document defines four exposure levels for Bitcoin outputs, with respect to an adversary who
can compute discrete logarithms on secp256k1, for example with a cryptographically relevant
quantum computer (CRQC): `EXPOSED_AT_REST`, `EXPOSED_ON_SPEND`, `NOT_EXPOSED` and `UNDETERMINED`.
The first two apply BIP 360's long exposure and short exposure to individual outputs. No deployed
output type is `NOT_EXPOSED`. A level depends only on the output and on the transactions confirmed
up to a given block. An implementation that lacks the data needed to decide assigns
`UNDETERMINED`.

## Motivation

Any count of the bitcoin a CRQC could take, and any wallet warning about it, has to decide cases
such as:

- a reused address that has been spent from and still holds funds;
- a P2TR output, whose output key is on the chain even if its internal key never was;
- a P2SH or P2WSH output whose script has not been revealed;
- a public key used under more than one address type;
- a public key disclosed outside the chain, for example through an extended public key.

[BIP 360](bip-0360.mediawiki) lists the output types that are vulnerable to long exposure and notes
that P2PKH, P2SH, P2WPKH, P2WSH and P2MR outputs become vulnerable once their script reveals a
public key. It does not say, for a given output, what counts as revealed, or what to report when
part of the chain data is missing. Without such rules, two tools can report different results for
the same output.

This document specifies those rules, with test vectors. It does not score risk. Appendix A suggests
a minimum action for each level.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHOULD", "SHOULD NOT", and "MAY" in this document
are to be interpreted as described in RFC 2119.

### Terminology

* **Adversary**: someone who can compute discrete logarithms on secp256k1, and can therefore
  produce a valid secp256k1 signature for any public key they know.
* **Public key**: a point on secp256k1, encoded as compressed (`02`, `03`), uncompressed (`04`),
  hybrid (`06`, `07`, with the prefix matching the parity of y) or x-only
  ([BIP 340](bip-0340.mediawiki)). An x-only key covers both points with its x-coordinate. Bytes
  that do not encode a valid point are not a public key.
* **Confirmed transaction**: a transaction in the evaluated block or one of its ancestors. A level
  is always assigned as of an evaluated block.
* **Revealed script**: a script that a confirmed transaction supplied to spend an output: a P2SH
  redeem script, a P2WSH witness script (including inside P2SH), or a leaf script from a P2TR or
  P2MR script-path spend, together with its leaf version and the Merkle path from its control block.
  A script counts as revealed whether or not consensus executes it: BIP 360 skips execution for a
  P2MR tree of depth zero, leaves of unknown versions are not executed, and a tapscript
  ([BIP 342](bip-0342.mediawiki)) in which decoding reaches an `OP_SUCCESSx` is valid without being
  executed. A spend counts as a P2SH or P2WSH spend only in a block where
  [BIP 16](bip-0016.mediawiki) or [BIP 141](bip-0141.mediawiki), respectively, is active, and as a
  P2TR or P2MR script-path spend only in a block where [BIP 341](bip-0341.mediawiki) or BIP 360,
  respectively, is active.
* **Published key**: a public key found in a confirmed transaction as follows:
  1. any data push in a `scriptPubKey` or `scriptSig`, any witness element, and any data push in a
     revealed script, whose bytes are a valid 33- or 65-byte public key;
  2. any valid x-only key that is a P2TR output key, the internal key in a P2TR control block, or a
     32-byte push in a revealed leaf script of leaf version `0xc0` (tapscript) that is immediately
     followed by `OP_CHECKSIG`, `OP_CHECKSIGVERIFY` or `OP_CHECKSIGADD`.

  A 32-byte value in any other position is not a published key.
  A script is read one instruction at a time from its start, up to its first instruction that
  cannot be decoded. Data inside a push is not read as a script unless it is a revealed script.
* **Long exposure** and **short exposure**: the two attacks defined in BIP 360, on public keys that
  are on the chain and on public keys that are in the mempool while a spend is unconfirmed.

Unconfirmed transactions, and blocks other than the evaluated block and its ancestors, MUST NOT
affect a level. See [Disclosure Outside the Chain](#disclosure-outside-the-chain).

### Exposure Levels

Levels are defined only for evaluated blocks at which BIP 16, BIP 141 and BIP 341 are active.
Outputs whose `scriptPubKey` begins with `OP_RETURN`, and witness version 0 outputs whose program is
neither 20 nor 32 bytes long, cannot be spent and are not classified. Every other output has
exactly one level: the first of the following that applies.

#### `NOT_EXPOSED`

The consensus rules of the output's type require a valid post-quantum signature for every spend. A
hybrid scheme that requires both a post-quantum and a secp256k1 signature qualifies. A type that
allows any spend without a post-quantum signature, including a spend that needs no signature,
does not. This level is a property of the output type. It MUST NOT be inferred from missing
information about a script, nor from an output being unspendable.

No deployed output type qualifies. P2MR does not, because its leaves can be satisfied without a
post-quantum signature. The level is reserved for future output types.

#### `EXPOSED_AT_REST`

This level is BIP 360's long exposure applied to a single output: each condition below is chain
evidence that the adversary can spend the output without waiting for its holder to broadcast a
spend, subject only to consensus rules such as coinbase maturity and timelocks.

An output is `EXPOSED_AT_REST` if any of the following holds:

1. **Key in the output.** The output is P2PK with a valid public key, bare multisig (`m`-of-`n`,
   with `n` at most 16) with valid public keys in at least `m` of its `n` key positions, or P2TR
   with a valid output key. A bare multisig output with `m` = 0 needs no signature and meets this
   condition.
2. **Revealed script.** A revealed script opens the output's commitment:
   * for the bytes `S` of any revealed script, the output is P2SH with script hash `HASH160(S)` or
     `HASH160(0x0020 ‖ SHA256(S))`, or P2WSH with program `SHA256(S)`;
   * for a revealed leaf script with its leaf version and Merkle path, where BIP 360 is active, the
     output is P2MR with root equal to the leaf hash or to any branch hash computed along that path
     as in BIP 360.
3. **Published key.** For one of the six encodings `e` of the two points with a published key's
   x-coordinate (compressed, uncompressed and hybrid), the output is P2PKH or P2WPKH with key hash
   `HASH160(e)`, or P2SH with script hash `HASH160(0x0014 ‖ HASH160(e))`.

The level follows from these conditions alone; no check is made that the adversary can complete a
spend. Condition 2 assumes that a confirmed spend makes public everything needed to spend another
output with the same commitment along the same path, except signatures, which the adversary can
produce. This includes paths that need no signature. The assumption usually holds, but the condition
does not check each case and can over-report, for example for a script that embeds a signature for
one particular transaction, a script that the other output's type interprets differently, or a
future path that requires a post-quantum signature. It can also over-report when a leaf script
revealed without being executed is matched as `S` for a P2SH or P2WSH output, which does execute
`S`: the revealing spend need not have shown data that execution requires, such as a hash preimage.

#### `EXPOSED_ON_SPEND`

The output is P2PKH, P2WPKH, P2SH, P2WSH or, where BIP 360 is active, P2MR, and no condition above
holds. Any spend of such an output reveals a public key or a script, which the adversary can
usually use to replace the spending transaction before it is confirmed. This is BIP 360's short
exposure.

An implementation MUST NOT assign this level unless it has checked the conditions that apply to the
output's type against every confirmed transaction. The level means only that those conditions do not
hold. It does not rule out that the adversary could rebuild the output's script from published keys,
which these rules do not attempt.

Once an output of one of these types has a confirmed spend in a block where the consensus rules of
its type are active, every other output with the same `scriptPubKey`, including any created later,
is `EXPOSED_AT_REST`.

#### `UNDETERMINED`

Any other output. This covers outputs whose script semantics the implementation does not
recognize, P2PK, bare multisig and P2TR outputs whose keys do not meet condition 1, witness
programs that have no assigned meaning, and outputs for which the implementation lacks the data
needed to assign another level.

### Missing Data

Implementations MUST NOT assign `NOT_EXPOSED`, `EXPOSED_AT_REST` or `EXPOSED_ON_SPEND` without
establishing that level's conditions, and assign `UNDETERMINED` where they cannot. `NOT_EXPOSED` and
condition 1 need no chain data. Two implementations with complete data for the same evaluated block
assign the same level. One with less data differs from them only by assigning `UNDETERMINED` to some
outputs.

For a P2PKH, P2WPKH, P2SH, P2WSH or P2MR output, a positive count of confirmed spends of its own
`scriptPubKey` establishes condition 2 or 3 without retrieving those spends, provided every spend
counted is in a block where the consensus rules of the output's type are active. A count of zero
does not establish `EXPOSED_ON_SPEND`, because the key or script may have been published under
another `scriptPubKey`.

Conditions 2 and 3 can be checked for any output against two indexes over all confirmed
transactions: one of `HASH160(e)` and `HASH160(0x0014 ‖ HASH160(e))` for the six encodings `e` of
each published key, and one of `HASH160(S)`, `HASH160(0x0020 ‖ SHA256(S))` and `SHA256(S)` for each
revealed script `S`, together with the leaf and branch hashes of each revealed leaf. An
implementation that has only an address or script-hash index can establish `EXPOSED_AT_REST` for a
P2PKH, P2WPKH, P2SH, P2WSH or P2MR output, for example through a positive count of spends of its
`scriptPubKey` as above, but not `EXPOSED_ON_SPEND`.

### Classification by Output Type

| Output type | `scriptPubKey` | Level |
| --- | --- | --- |
| P2PK | `<pubkey> OP_CHECKSIG` | `EXPOSED_AT_REST` (condition 1) |
| Bare multisig | `OP_m <pubkey> ... <pubkey> OP_n OP_CHECKMULTISIG` | `EXPOSED_AT_REST` (condition 1) |
| P2TR | `OP_1 <32 bytes>` | `EXPOSED_AT_REST` (condition 1) |
| P2PKH | `OP_DUP OP_HASH160 <20 bytes> OP_EQUALVERIFY OP_CHECKSIG` | `EXPOSED_ON_SPEND` unless condition 3 holds |
| P2WPKH | `OP_0 <20 bytes>` | `EXPOSED_ON_SPEND` unless condition 3 holds |
| P2SH | `OP_HASH160 <20 bytes> OP_EQUAL` | `EXPOSED_ON_SPEND` unless condition 2 or 3 holds |
| P2WSH | `OP_0 <32 bytes>` | `EXPOSED_ON_SPEND` unless condition 2 holds |
| P2MR, where BIP 360 is active | `OP_2 <32 bytes>` | `EXPOSED_ON_SPEND` unless condition 2 holds |
| `OP_RETURN`, or witness version 0 of another length | `OP_RETURN ...`, or `OP_0` then `<2 to 40 bytes>` other than 20 or 32 | Not classified |
| Any other witness version or program length | `OP_1` to `OP_16`, then `<2 to 40 bytes>` | `UNDETERMINED` |
| Any other script | | `UNDETERMINED` |

In this table, `<20 bytes>`, `<32 bytes>` and `<2 to 40 bytes>` are direct pushes, so each of these
templates matches one exact byte layout. `<pubkey>` is a push of 33 or 65 bytes in any push form,
and `m` and `n` are encoded as `OP_0` to `OP_16`, with `m` not greater than `n`. Whether the keys
are valid is decided by condition 1. P2SH-wrapped witness outputs are P2SH outputs. The levels
assume complete data; see [Missing Data](#missing-data).

**P2TR.** The output key `Q` is in the `scriptPubKey`, and an adversary who computes its discrete
logarithm can spend the output through the key path. Consensus does not check how `Q` was
constructed, so this holds for outputs meant to be spent only through the script path, including
those whose internal key has no known discrete logarithm.

**P2MR.** [BIP 360](bip-0360.mediawiki) defines P2MR, which has no key path. Condition 2 applies to
it, including leaves revealed by P2TR spends of the same tree. Until BIP 360 is active, a witness
version 2 output with a 32-byte program has no assigned meaning and is `UNDETERMINED`.

### Disclosure Outside the Chain

The following disclose public keys or scripts without evidence in the chain up to the evaluated
block, and do not affect a level:

* a transaction that was broadcast but never confirmed, or was replaced;
* a block that is neither the evaluated block nor one of its ancestors;
* a spend on another chain that shares part of Bitcoin's history;
* an extended public key given to a third party, which reveals every non-hardened child key,
  including keys of outputs never spent;
* use of the key in another protocol, such as a sidechain;
* compromise of the key holder.

A level of `EXPOSED_ON_SPEND` therefore does not show that a key or script was never disclosed.
Implementations that learn of such a disclosure can report it separately.

## Rationale

**Four levels.** A single exposed/not-exposed flag would put long-exposure and short-exposure
targets in one bucket. `EXPOSED_AT_REST` outputs are a more urgent target for migration, since they
are likely to become viable targets sooner than `EXPOSED_ON_SPEND` outputs. `UNDETERMINED` lets an
implementation say that it cannot tell. No output type is `NOT_EXPOSED` today; defining the level
now reserves it for future output types whose consensus rules require a post-quantum signature for
every spend.

**Focus on attacker capability.** The classification describes what the adversary can do under
current consensus rules, using deterministic criteria based on chain data. Whether the holder knows
something the adversary lacks, such as an unrevealed P2TR internal key, does not affect the
classification. Whether an output key was tweaked cannot be told from the key, and would not stop a
key-path spend if it could. Recovery protocols are out of scope.

**One level for all three conditions.** The three conditions of `EXPOSED_AT_REST` all point to
long exposure, so they share one level. A separate level for outputs exposed by a revealed script
or a published key would suggest that they are safer than P2PK.

**What counts as revealed.** A spend reveals the script it uses. Other outputs that commit to the
same script bytes through P2SH, P2WSH or P2SH-P2WSH are exposed, and so are P2MR outputs whose root
matches the one computed from the revealed leaf and Merkle path. This includes scripts that need no
signature. Public keys alone do not reveal a script: an output whose script combines published
keys stays `EXPOSED_ON_SPEND` until its own script is revealed, because these rules do not rebuild
scripts from known keys. Condition 3 is the exception. It covers P2PKH and P2WPKH, which commit to
the hash of one key, and P2SH-P2WPKH, the P2SH form of P2WPKH, so a published key gives a fixed set
of hashes to compare. Other single-key scripts fall under condition 2 once a spend reveals the
script. A closed list keeps implementations consistent where an open rule, such as any script the
adversary could rebuild from published keys, would not. The cost is that condition 3 does not flag
an output with another single-key script even when the adversary can rebuild that script from a
published key.

**Beyond the spent output.** A simpler rule would expose only outputs whose own `scriptPubKey` has a
confirmed spend. It would miss exposures that need no search: the genesis coinbase key is in a P2PK
output while its P2PKH address holds tens of thousands of unspent outputs at the time of writing,
one witness script can be paid through both its P2WSH and P2SH-P2WSH forms, and BIP 360 describes
moving script trees from P2TR to P2MR, where a leaf revealed by a P2TR spend then opens the P2MR
output.

**x-only keys.** An x-only key is read only where its position shows that it is a key, because
about half of all 32-byte values, hashes included, are valid x-coordinates.

**Chain data only.** Mempool contents differ between nodes and change over time, so a level based
on them could not be reproduced later. An implementation that cannot see the whole chain reports
`UNDETERMINED` where it cannot decide, so it never contradicts one with complete data.

**Unassigned witness programs.** Current consensus rules give these witness versions and program
lengths no meaning of their own, so most such outputs can be spent by anyone. A later soft fork
could add rules for them, and an implementation cannot know whether one has activated since it was
written, so it assigns `UNDETERMINED`.

**No scoring.** A risk score would need a subjective formula that weighs quantities such as coin
value and dormancy for an unknown holder. This document classifies outputs by what the chain shows
and leaves risk judgments to users and wallets.

**Relationship to BIP 360.** BIP 360 defines long and short exposure and lists the output types
that are vulnerable to long exposure; the table in
[Classification by Output Type](#classification-by-output-type) starts from that list. BIP 360
also defines P2MR, which this document classifies where BIP 360 is active. The other rules do not
depend on BIP 360 being active.

## Appendix A: Holder Implications (Informative)

The table pairs each level with an action identifier and the minimum advice, so that wallets that
warn about quantum exposure give the same basic advice. Wording, reasons and urgency are left to
the wallet.

| Level | Action | Minimum advice |
| --- | --- | --- |
| `EXPOSED_AT_REST` | `MIGRATE` | Move the funds once a destination the holder trusts is available. Until then, send no more funds to the same script. |
| `EXPOSED_ON_SPEND` | `SWEEP_WHEN_SPENDING` | Stop giving out the address. When spending, spend the outputs that pay the same script together where possible, and send no change or new funds back to it. Once the wallet's spend confirms, any remaining or later outputs to that script are `EXPOSED_AT_REST`. |
| `NOT_EXPOSED` | `NONE` | No action. |
| `UNDETERMINED` | `MIGRATE` | As for `EXPOSED_AT_REST`, unless the wallet can get the data to classify the output. |

Funds moved from an `EXPOSED_AT_REST` or `UNDETERMINED` output should go to a `NOT_EXPOSED` output
type if one is available, or else to a fresh output of a type that is `EXPOSED_ON_SPEND`. Wallets
should tell users which destinations they support.

## Backward Compatibility

This document does not change consensus, relay policy or the peer-to-peer protocol, and it does not
say how the results of other classifications map onto its levels. Implementations should state
which version of this document their results follow.

## Reference Implementation

A Python implementation that uses only the standard library is available at
[duncan0k/pubkey-exposure-classification](https://github.com/duncan0k/pubkey-exposure-classification).

It takes an output's `scriptPubKey` and a description of the chain data available for it, and runs
every vector in this document. The vectors are also published there as `test_vectors.json` under
CC0-1.0.

## Changelog

* __0.7.0__ (2026-11-05):
    * `EXPOSED_AT_REST` is now defined by three conditions: a key in the output, a revealed script,
      or a published key for P2PKH, P2WPKH and P2SH-P2WPKH outputs. A revealed script also exposes
      outputs that commit to the same script through P2SH, P2WSH or P2SH-P2WSH, and a leaf and
      Merkle path revealed in a P2TR or P2MR spend expose a P2MR output with the resulting root.
    * Revealed scripts that need no signature now give `EXPOSED_AT_REST`.
    * Missing data now gives `UNDETERMINED`. A positive count of spends of an output's own
      `scriptPubKey` still establishes `EXPOSED_AT_REST`; a count of zero no longer establishes
      `EXPOSED_ON_SPEND`.
    * Levels are defined only for evaluated blocks at which BIP 16, BIP 141 and BIP 341 are active,
      and a spend reveals a script only in a block where the soft fork for its type is active.
    * Witness version 2 outputs are `UNDETERMINED` until BIP 360 is active. P2PK, bare multisig and
      P2TR outputs without enough valid keys are `UNDETERMINED`. `OP_RETURN` outputs and witness
      version 0 outputs of invalid length are not classified.
    * Appendix A maps `UNDETERMINED` to `MIGRATE`; `TREAT_AS_MIGRATE` is removed.
* __0.6.1__ (2026-10-19):
    * `NOT_EXPOSED` requires a post-quantum signature on every spending path and takes precedence
      over `EXPOSED_AT_REST`. Hybrid schemes qualify.
* __0.6.0__ (2026-09-24):
    * `EXPOSED_ON_SPEND` covers outputs that pay the same script, and Appendix A recommends
      spending them together.
* __0.5.0__ (2026-09-18):
    * P2MR moved from `NOT_EXPOSED` to `EXPOSED_ON_SPEND`. `NOT_EXPOSED` became a property of an
      output type's consensus rules. The BIP type changed to Informational.
* __0.4.0__ (2026-09-14):
    * Added Appendix A with an action identifier per level.

    * Initial draft.
